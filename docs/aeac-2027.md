# AEAC 2027 competition integration

This document specifies the AEAC 2027 competition-specific integration for
NOMAD. It is subordinate to the [PRD](prd.md) and
[architecture](architecture.md): organizer requirements come from the CONOPS
inventory, while this document owns the external-server contract and the
competition module boundary.

The reusable NOMAD core must remain competition-agnostic. AEAC-specific wire
formats, credentials, cadence rules, scoring diagnostics and traffic translation
belong in an opt-in competition module, not in vehicle, mission, safety or
MAVLink implementation code.

## Official source and current portal status

Official competition portal:
<https://aeac.mylonics.com/#/>

The supplied CONOPS states that the competition connection token and server
documentation are provided through the named competition portal
(AE27-NET-001). The portal responds as **AEAC Student Competition Server**, but
its documentation is rendered client-side; the available text-only retrieval in
this review did not expose the interactive connection instructions or wire
schema. No token was requested and no competition traffic was transmitted.

Therefore the sections below intentionally separate source-confirmed behavior
from portal details that still need to be transcribed and tested. Do not infer an
HTTP, WebSocket, MQTT, JSON, protobuf or other transport merely from the portal
being a web application.

## Confirmed competition behavior

The following is source-confirmed from CONOPS v1.0 and is independent of the
portal's eventual wire encoding.

### Ownship telemetry

While the Task 1 UAV is armed, NOMAD must send competition telemetry at 1 Hz.
The logical payload contains:

| Logical field | Required semantics |
|---|---|
| UAV identifier | Bidder-defined string identifier |
| Timestamp | Unix timestamp; exact wire unit remains Q04 |
| Latitude | Decimal degrees |
| Longitude | Decimal degrees |
| Altitude | AGL metres |
| Horizontal accuracy | Metres |
| Vertical accuracy | Metres |
| Battery | Percentage, 0 through 100 |
| Mode | `off`, `idle`, `link-lost`, `failsafe`, `armed-pilot`, or `armed-automatic` |
| RC link quality | Bidder-defined normalized float from 0 through 1, with 1 best |
| Telemetry link quality | Bidder-defined normalized float from 0 through 1, with 1 best |

The core owns the source value, validity and age of those measurements. The AEAC
module owns mapping them into the official wire schema. Home-relative or MSL
altitude must not be labelled AGL without the reviewed conversion. GPS fix type
or satellite count must not be substituted for horizontal/vertical accuracy.

Relevant scoring behavior must also be reproducible in tests: at least 300 s of
armed telemetry is the positive baseline; missing telemetry begins a disconnect
penalty at 30 s and continues at 15 s intervals; packet spacing greater than
1.1 s or less than 0.4 s is penalized; startup while already armed and invalid
GPS while armed are penalized. The CONOPS latency wording is ambiguous and
remains Q04 rather than an implementation rule.

### Traffic feed

The competition server supplies flying-UAV traffic, including simulated UAVs,
at 1 Hz. NOMAD must react to the traffic and keep its own UAV outside each other
UAV's cylindrical radial and vertical exclusion zone.

The competition module translates server-native traffic records into generic
NOMAD traffic observations. The reusable core owns freshness policy,
deconfliction, mission consequences and operator advisories. A missing or stale
traffic feed means traffic state is unknown, never clear.

Exact traffic field names, altitude datum, cylinder radius/vertical semantics,
sequence/timestamp behavior, velocity availability, equality at a boundary,
freshness and right-of-way remain Q04 until the portal/organizers define them.

## NOMAD module boundary

AEAC support is an optional application module. It must not become a dependency
of the reusable core and it must not introduce a generic dynamic plugin
framework merely to host one competition integration.

Target dependency direction:

```text
AEAC 2027 module  --->  public NOMAD application/domain boundary  --->  NOMAD core
       |
       +---------------- official competition server

NOMAD core  -X->  AEAC types, endpoints, token handling or scoring rules
AEAC module -X->  MAVSDK/MAVLink transport or direct vehicle actuation
```

The module owns:

- official endpoint/session/authentication handling;
- wire serialization and deserialization;
- the 1 Hz telemetry scheduler and competition-specific rate diagnostics;
- reconnect/error handling and bounded networking queues;
- mapping generic telemetry into the official six-state mode and server schema;
- validating and translating server traffic into generic traffic observations;
- server receipt/latency evidence and competition-specific scoring diagnostics;
- redaction of tokens and sensitive server/session data from logs.

The core owns:

- authoritative telemetry values, source identity, validity and age;
- mission state and vehicle state;
- command validation and all vehicle decisions;
- traffic freshness/safety policy and deconfliction decisions;
- payload authorization and hazardous-output policy;
- MAVSDK/MAVLink and ArduPilot interaction.

The narrow integration seam should therefore look conceptually like two boring
operations: read a generic, immutable ownship telemetry snapshot; submit a
validated generic external-traffic observation. The exact C++ boundary belongs
to G2/G4 and should be implemented only when the persistent runtime exists. Do
not copy AEAC field names into generic core models solely to mirror the server.

## Target repository layout

The intended shape is an opt-in module rather than `#ifdef AEAC` branches spread
through the core:

```text
modules/
└── aeac_2027/
    ├── CMakeLists.txt
    ├── include/              # AEAC module public surface only
    ├── src/                  # protocol/auth/mapping/network implementation
    └── tests/                # wire fixtures, rate, reconnect and traffic tests
```

A competition composition target may link this module with the normal NOMAD
runtime. A non-competition build does not need the module and should have no
AEAC dependency. Future event-specific integrations can be separate modules that
reuse the same generic application/domain boundary without a central registry.

## Runtime flow

1. Start the reusable NOMAD runtime and establish the selected ArduPilot link.
2. Start the AEAC module with deployment-provided credentials and official server
   settings. Connecting before arming is a project strategy, not a CONOPS cadence
   requirement.
3. Establish traffic reception and report module health before flight readiness.
4. When armed, sample a fresh core telemetry snapshot and publish on the required
   1 Hz schedule. Track scheduled, sent and server-received times separately.
5. Validate every inbound traffic record, translate it to generic units/types and
   submit it to the core with source and receive timestamps.
6. On feed loss, authentication failure or stale traffic, report degraded/failed
   state. Do not silently declare the sky clear and do not replay stale ownship
   positions as current data.
7. On shutdown/disarm, preserve bounded evidence needed for scoring and testing,
   then close the external connection according to the official contract.

## Verification plan

G4 must not close on a successful socket connection alone. At minimum, automated
or replayable tests need to prove:

- exact official schema and authentication against a mock derived from the
  transcribed portal contract;
- 1 Hz armed scheduling, including the 0.4 s and 1.1 s scoring boundaries;
- stale/invalid telemetry is not relabelled as valid competition data;
- mode precedence for overlapping link-loss/failsafe/armed states;
- disconnect, reconnect, duplicate, reordered and malformed server traffic;
- multiple independent traffic tracks and exclusion cylinders;
- stale traffic produces unknown/degraded state, not a clear condition;
- credentials are never emitted in ordinary logs or committed fixtures;
- the AEAC module has no direct MAVLink command path;
- official-server acceptance using a non-production test session when the
  organizers provide one.

The official portal contract, Q04 organizer clarifications and the numeric D08
freshness/latency budgets remain prerequisites for release acceptance.
